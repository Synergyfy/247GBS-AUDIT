# PHASE 25

## Scheduled Re-Audit

Rather than ending with the first report, the platform should prompt businesses to perform periodic re-audits (for example every 3, 6, or 12 months, depending on their programme).

Each re-audit compares:

* Previous audit vs. current audit
* Problems resolved
* New issues detected
* Improvement trends
* Remaining opportunities

This reinforces Henry's concept that the audit is an ongoing business improvement process rather than a single questionnaire.

---

## How this differs from the current implementation

From Henry's comments and the current prototype, the main gaps are:

* The current flow does not clearly separate **Triage** from the main audit.
* Users should not manually choose Short vs. Long Audit; the system should decide after triage.
* Sector-specific question sets need to replace generic questions.
* The audit should be organized into clearly defined stages rather than only showing percentage completion.
* Questions need to capture actionable business data, not just yes/no responses.
* Budget and desired time-to-results must be collected before recommendations.
* The recommendation engine must produce tailored, business-specific implementation plans instead of generic advice.
* The audit must transition directly into the Account Manager and proposal workflow.
* The platform should support continuous monitoring and scheduled re-audits, making the audit the foundation of an ongoing consultancy relationship rather than a standalone form.

This end-to-end flow aligns with Henry's repeated description of the audit as a **business diagnostic, prioritization, and solution delivery system**, not merely an assessment form.
